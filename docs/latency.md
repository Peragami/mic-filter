# 遅延設計（2026-11-08 たくみさん希望：限りなくゼロ）

## 先に結論
うちのアプリが足す遅延は **実質ゼロ** にできる。残るのは機器とWindowsドライバと
接続先アプリ分で、ここは設計で「踏まない」ようにするのが仕事。

## 内訳（48kHz）
| 要因 | 遅延 | 対策 |
|---|---|---|
| DSP処理（今のチェーン） | **0サンプル** | IIR式で1サンプルずつ処理。見越し（ルックアヘッド）なし |
| 処理時間そのもの | 0.006ms以下/ブロック | 制限時間の0.2%しか使ってないので待ちにならない |
| 入力バッファ 64サンプル | 1.33ms | 既定64、安定すれば32（0.67ms）も選択可 |
| 出力バッファ 64サンプル | 1.33ms | 同上 |
| サンプルレート変換 | 0にする | 入力〜出力まで48kHzに統一。変換が入ると数ms＋音質劣化 |
| Windowsミキサー（共有モード） | 約10〜30ms | **WASAPI排他モード優先**で回避。ダメなら IAudioClient3 低遅延共有 |
| USBマイク/オーディオI/F自体 | 約1〜5ms | 機器側、削減不可。有線前提 |
| 仮想ケーブル（VB-CABLE等）経由時 | 約5〜20ms追加の見込み | ケーブル側のバッファ。ゼロにはできない |
| Discord等の接続先 | 接続先のジッタバッファ分 | 制御外 |

**アプリ単体の往復目標：約3〜6ms**（WASAPI排他、64〜128サンプル、機器分除く）。
共有モードで組むと平気で20〜40msになるので、そこが一番の分かれ目。

## 入れると遅延が増えるもの（要注意）
- FFT系フィルター／リニアフェーズEQ：窓の分だけ遅れる（1024FFT=約21ms）
- ルックアヘッド付きリミッター/コンプ：見越し分（1〜5ms程度〜）
- AIノイズ抑制：フレーム処理＋見越しで約10ms〜が相場。これを入れるかは遅延とのトレードオフで別途判断

## シナリオ試算：クライアント → VB-CABLE → Discord、EQ＋リップノイズ除去あり（2026-11-08）
前提：48kHz、EQはIIR方式（遅延0）、リップノイズ除去は見越し方式。
相手に届くまでのネットワーク分は含まない（Discordの送信・相手側ジッタは別途数十ms）。

| 項目 | 最良 | 典型 | 悪い条件 |
|---|---|---|---|
| マイク機器自体 | 1ms | 3ms | 5ms |
| 入力バッファ 64（悪条件128） | 1.3 | 1.3 | 2.7 |
| EQ | 0 | 0 | 0 |
| リップノイズ除去の見越し 64〜128 | 1.3 | 2.7 | 2.7 |
| 出力バッファ 64（悪条件128） | 1.3 | 1.3 | 2.7 |
| VB-CABLE 内部 | 5 | 10 | 20 |
| Discord の取り込み（10〜20msフレーム） | 10 | 10 | 20 |
| **合計** | **約20ms** | **約28ms** | **約53ms** |

- うちのアプリ分だけなら **4.0〜5.3ms**。残りは機器・ケーブル・Discord側。
- リップノイズ除去について：クリック音は「出た後を見て直す」処理なので、見越しゼロでは正確に消せない。64サンプル（1.3ms）でも簡易版は可能、128（2.7ms）が精度とのバランス点。FFT方式にすると10〜20ms増えるので使わない。

## 一番速い経路の本音
仮想ケーブル経由（クライアント→VB-CABLE→Discord）が一番遅延の底上げ要因。
遅延最優先なら、**VSTを直接読めるホスト（OBS等）で使う経路が最速**で、
クライアント経由は「VSTが読めないアプリ用」と位置づけるのが正しい。
