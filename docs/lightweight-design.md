# 最軽量構成（2026-11-08 たくみさんの希望で決定）

結論：**C++、フレームワークなし。JUCEは使わない。**

理由：重さの正体は言語よりフレームワークとDSPアルゴリズム。
基本チェーン（EQ/ゲート/コンプ等）はどのネイティブ言語でも誤差レベル。
JUCEは開発が速い代わりに土台ごと入るので、最軽量とは相性が悪い。

## 構成

| 部分 | 採用 | 入れないもの |
|---|---|---|
| DSPコア | 自前ヘッダのみ `Source/dsp/PureDsp.h`（依存は `<cmath>` だけ） | JUCE DSP、外部ライブラリ |
| VST3 | 公式 VST3 SDK を直接使用。GUIなし（パラメーターはホストの汎用UIで操作）から開始 | VSTGUI（重いので後回し、要れば最小追加） |
| クライアント | Win32 API + WASAPI 直接。`.vst3` をCOMとして読み込んでホストする | Electron、.NET、Qt、JUCE |
| ランタイム | なし（静的リンク最小構成） | GC系言語（C#/Go/Python）はリアルタイム音声で不利なので不採用 |
| Rust案 | CPUはC++と同等だが、VST3公式SDKがC++のため橋渡し分だけ不利＋開発難度↑。不採用 | nih-plug |

## 実測（DSPコア単体、こちらのVMで計測 ※Windows実機値ではない）
- 48kHz / 128サンプルブロック： **1ブロック 5.81µs**（制限時間 2667µs の約0.2%）
- 言い換え：**1コアの約0.22%**、458倍速で処理できる
- テスト用実行ファイル自体が 17KB（コアのコード量の小ささの参考）

つまり基本フィルターでは、たくみさんのPC（i5-1334U）でも体感ゼロを目指せる。
逆に言えば、将来AIノイズ抑制を入れるとそっちが支配的になる（言語では解決しない）。

## 目標値（Windows実機で要検証、約束値ではない）
- クライアント exe：数百KB以下
- メモリ：15MB以下
- 音声処理CPU：1%未満（基本チェーン、48kHz）

## 代償（正直なとこ）
- 開発はJUCEより手間がかかる（デバイス列挙、VST3読み込み、パラメーター同期を自前で書く）
- GUIは質素になる（Win32標準部品）
- バグの責任範囲が全部こっちになる

旧JUCE版（CMakeLists.txt / PluginProcessor等）は比較用に残してあるが、今後は PureDsp ベースで進める。

## C++ vs Rust 実測（2026-11-08、同条件ベンチを両言語で実装してVMで計測）
| | C++ (-O2) | Rust (-O + LTO) |
|---|---|---|
| 128サンプル処理 | 5.6〜6.0µs | 2.4〜2.9µs |
| 1コア占有 | 約0.21% | 約0.10% |
| 実行ファイル（strip後） | **15KB** | 316KB |

- CPU差は絶対値で 0.1ポイント程度。制限時間2667µsに対して両方とも誤差レベルで、体感差は出ない。実装（float演算の書き方等）で逆転しうる差。
- サイズは C++ が明確に小さい（Rustは標準ライブラリ静的リンク分が乗る。実アプリではGUI/OS分が加わり差は相対的に縮む）。
- 決め手は速度ではなく相性：VST3公式SDKとWASAPIがC++ネイティブで、Rustだと橋渡し（FFI/ラッパークレート）分が増える。
